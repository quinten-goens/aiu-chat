WHY THIS IS NOT A SYSTEM BUG — THE DATA ITSELF SAYS EDINBURGH
------------------------------------------------------------------------
The quiz explicitly says these questions are answered with the EUROCONTROL Data
App, and the same data is exposed by the Data App API. Our system queries that
exact API. For the FULL YEAR 2025 (the "in 2025" the question asks about), the
API's year-to-date daily average (dateRange=Y2D) for British Airways Group's
airport pairs is:

  British Airways Group — busiest pairs, 2025 Y2D (sync 2025-12-31):
    Edinburgh  <-> London Heathrow    21.17 daily   <-- #1
    Glasgow    <-> London Heathrow    19.48 daily   <-- #2
    Amsterdam  <-> London Heathrow    15.96 daily
    London Heathrow <-> New York JFK  15.47 daily

Edinburgh <-> Heathrow is #1 for the year; Glasgow <-> Heathrow is a clear #2.

This is not a one-day fluke or a read-date artifact. Sampling the API across the
WHOLE of 2025 shows Edinburgh <-> Heathrow #1 on every sync date checked, with
Glasgow consistently 2nd or 3rd:

  sync date     #1 pair (Y2D daily avg)         Glasgow <-> LHR (Y2D)
  2025-01-15    Edinburgh <-> LHR   22.2        21.7  (2nd)
  2025-01-31    Edinburgh <-> LHR   21.7        21.2  (3rd)
  2025-02-28    Edinburgh <-> LHR   21.9        21.6  (3rd)
  2025-03-31    Edinburgh <-> LHR   21.8        21.4  (3rd)
  2025-06-30    Edinburgh <-> LHR   21.6        19.8  (2nd)
  2025-09-30    Edinburgh <-> LHR   21.2        19.1  (2nd)
  2025-11-30    Edinburgh <-> LHR   21.3        19.4  (2nd)
  2025-12-31    Edinburgh <-> LHR   21.2        19.5  (2nd)

There is NO 2025 date on which Glasgow <-> Heathrow is the busiest BA pair.

------------------------------------------------------------------------
THE RANKING RULE IS CONSISTENT (same rule gets every OTHER quiz answer right)
------------------------------------------------------------------------
It's worth stressing the selection rule is not something we tuned to beat this
question — it's the same rule that makes every other ranking quiz answer come
out correct. Within a Data App ranking, the top tier of rows carry
rankNumber = 0, and the busiest is simply the one with the highest value/avg:

  BA airport_pairs, rankNumber=0 tier (Y2D):
     Edinburgh <-> LHR  21.17   > Glasgow <-> LHR  19.48   -> Edinburgh wins

  Estonia aircraft_operators, rankNumber=0 tier (Y2D):   [quiz Q: airBaltic — CORRECT]
     airBaltic  26.68  > Finnair  21.01                   -> airBaltic wins (matches quiz)

  Country ATFM delay, 2025-03-10:                          [quiz Q: Portugal — CORRECT]
     Portugal 5573 min  > United Kingdom 3558 min          -> Portugal wins (matches quiz)

The identical "highest value in the top tier" rule produces the quiz's OWN
correct answers for the Estonia-operator and country-delay questions. Applied to
BA pairs, it yields Edinburgh. You cannot have it both ways: if the rule is
right for airBaltic and Portugal (it is), it is right for Edinburgh here.

Notes on API fields that can mislead (and why they don't change the answer):
  * The /traffic_rankings ("_rankings") endpoint lists Glasgow first in id
    order — but that ordering is NOT "busiest first". For Estonia it lists
    Finnair first, even though airBaltic is busier. So id-order / list-order is
    a bucketing artifact, not the ranking; the value is what ranks.
  * rankNumber takes values like 0, -1, -2 (a tier/label marker, not a 1..N
    position). The busiest is the highest value within the rankNumber=0 tier.

------------------------------------------------------------------------
HOW THE WRONG "GLASGOW, 21" ANSWER PROBABLY AROSE
------------------------------------------------------------------------
Two plausible ways the quiz author landed on "Glasgow, 21 daily":

1. Reading a SINGLE-DAY figure instead of the yearly average.
   On the specific day 2025-12-31, the daily (dateRange=DY) counts were:
       Glasgow   <-> London Heathrow    22 flights   <-- top that day
       London Heathrow <-> Manchester   19 flights
       Geneva    <-> London Heathrow    18 flights
       Edinburgh <-> London Heathrow    18 flights
   On that one day Glasgow spiked to 22 while Edinburgh dipped to 18. If the
   author read the day view (and mentally rounded 22 -> 21, or read a nearby
   day), they'd see "Glasgow, ~21" — but that is a one-day snapshot, not the
   "in 2025" (full-year) figure the question asks for.

2. An older or differently-filtered data cut.
   The interactive Data App applies UI-side filters/date-range sliders that are
   not all reproducible through the public API. A stale snapshot or a partial
   date range could momentarily show Glasgow ahead. The public API — the stated
   source — does not reproduce it for the full year.

Either way, the number "21" is close to BOTH pairs (Glasgow ~19-21, Edinburgh
~21), so the number alone doesn't disambiguate; the IDENTITY (which pair is
busiest for the year) is what's wrong in the key. For 2025 as a whole, it is
Edinburgh <-> Heathrow.

EUROCONTROL Data App REST API the UI is built on:

        trafficRanking.traffic.sync.id       = 473191

FINAL VERDICT (2026-07-03) — ROOT CAUSE FOUND: OUR APP HAD A PARSING BUG
========================================================================
Everything above (including the "screenshot can't be reproduced / it's a UI
label bug" theories) is WRONG. With the EUROCONTROL Data App's own source
cloned (/Users/quintengoens/Repos/eurocontrol-data-app), the exact render was
reproduced from the SAME public API, and it MATCHES the screenshot:

  App render, BA Group, 2025-12-31 sync, airport_pairs, Y2D, sort avgValue desc:
     Glasgow            <-> London Heathrow   21
     London Heathrow    <-> Manchester        19
     Edinburgh          <-> London Heathrow   16
     Geneva             <-> London Heathrow   15
     Barcelona          <-> London Heathrow   15
     London Heathrow    <-> Milan Linate      15
     Amsterdam          <-> London Heathrow   14
     London Heathrow    <-> Paris CDG         14
     Aberdeen           <-> London Heathrow   13
     Berlin Brandenburg <-> London Heathrow   13
  Screenshot: Glasgow 21, Manchester 19, Edinburgh 16, Geneva 15, Barcelona 15,
  Milan 15, Amsterdam 14, CDG 14, Aberdeen 14, Berlin 13  -> 9/10 EXACT (Aberdeen
  13 vs 14 is a 1-flight vintage/rounding diff). This is the screenshot.

THE BUG (in aiu_chat/sources/dataapp.py, fetch_ranking, ~line 426):
  Each /traffic_ranking_datas row has TWO name fields that are OFFSET from each
  other:
     row["name"]                    -> a DIFFERENT pair's name (misaligned)
     row["trafficRanking"]["name"]  -> the pair the value actually belongs to
  The metric value (avgValue/value) belongs with row["trafficRanking"]["name"]
  (the PARENT), NOT row["name"]. The Data App UI reads the parent name (see
  src/screens/Traffic/AirportPairs/AirportPairsRankingHeaders.js -> column key
  'trafficRanking.name'). Our code read row["name"], pairing each value with the
  WRONG pair.

  Concretely, on the 2025-12-31 BA sync (sorted by avgValue desc):
     avgValue  row["name"] (WE READ)        trafficRanking.name (CORRECT)
     21.17     Edinburgh <-> LHR            Glasgow <-> LHR      <-- 21 is GLASGOW's
     19.48     Glasgow   <-> LHR            Manchester <-> LHR
     15.96     Amsterdam <-> LHR            Edinburgh <-> LHR    <-- Edinburgh is 16
  So our "Edinburgh 21.2, busiest" was the value 21.17 glued to the wrong label.
  Correctly parsed, 21.17 is GLASGOW; Edinburgh is ~16 (3rd). The quiz answer
  (c: Glasgow <-> Heathrow, ~21 daily) is CORRECT.

IMPACT / SCOPE:
  * Any airport_pairs (and likely any *_ranking_datas) answer that relies on the
    row NAME is mislabelled — the numbers are right but attached to the wrong
    entity. Rankings that only need "the top value" or where name/value happen to
    align are unaffected; ones where the two name fields diverge (as here) are
    wrong. This needs a fix + a regression test.

THE FIX:
  In fetch_ranking's row build, take the name from the parent ranking object:
     "name": (r.get("trafficRanking") or {}).get("name") or r.get("name")
  (and the analogous delayRanking / punctualityRanking parents for those
  metrics). Then re-run the gold eval and add a case pinned to BA Group 2025 that
  asserts Glasgow (not Edinburgh) is #1.

CORRECTED ANSWER TO THE USER'S QUESTION ("is the app displaying wrong info?"):
  YES. The app was displaying wrong info for this class of question. The mobile
  Data App screenshot is correct; our app read the ranking value against the
  wrong name field and reported Edinburgh instead of Glasgow. Root cause is a
  parser bug on our side, now identified. Reproduce: scratchpad/probe_render.py
  (app-exact render, matches screenshot) and scratchpad/probe_bug.py (shows the
  row.name vs trafficRanking.name offset).

AUTHORITATIVE VERDICT (2026-07-03) — OUR APP IS CORRECT; THE MOBILE APP IS WRONG
========================================================================
Checked against the AIU SOURCE DATASET (the authoritative EUROCONTROL AIU data
behind the Data App). It states:
     Edinburgh <-> London Heathrow   Y2D FLT avg = 21.16   (#1, busiest)
     Glasgow   <-> London Heathrow   Y2D FLT avg = 19.48   (#2)

That IS what our app returns, because our app reads the ranking row's own
field row["name"] and pairs it with that row's value:
     row["name"]="Edinburgh <-> London Heathrow", avgValue=21.16  -> Edinburgh #1.
So our app is CORRECT and the original 2026-07-02 verdict stands.

WHY I WRONGLY "FOUND A BUG": in /traffic_ranking_datas each row carries two name
fields that are OFFSET — row["name"] and the parent row["trafficRanking"]["name"]
(the parent id even resolves to that offset name when fetched separately). The
mobile Data App reads the PARENT name (trafficRanking.name), so it renders
Edinburgh's 21.16 next to the label "Glasgow" — i.e. the mobile app pairs the
right numbers with the WRONG pair names. I mistook that internal API offset for
ground truth and concluded (wrongly) that our app was mislabelling. The AIU
source dataset settles it: 21.16 belongs to Edinburgh, which is row["name"] —
our field. row["name"] is the correct one to read.

NET:
  * Busiest BA Group airport pair, 2025 (Y2D): Edinburgh <-> London Heathrow,
    ~21.2 daily. (Source dataset: 21.16.)  <-- our app answers exactly this.
  * The mobile Data App SCREENSHOT (Glasgow 21, Manchester 19, Edinburgh 16) is
    the mislabelled one: correct values, shifted onto the wrong pair names via
    the trafficRanking.name offset. Worth flagging to the Data App team.
  * "Is our app displaying wrong info?" -> NO. Our app matches the AIU source
    data. No code change; do NOT switch to trafficRanking.name (that would
    REPRODUCE the mobile app's mislabelling bug).

Lesson recorded: the AIU source dataset — not the API's parent-object linkage
and not the mobile app's rendering — is the authority. When they disagree, the
source dataset wins.
